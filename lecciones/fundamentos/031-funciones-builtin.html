Las funciones built-in

El bucle que no tenías que escribir — unas setenta funciones que ya están ahí, sin importar nada

En la lección anterior dominaste el bucle while de arriba abajo. Esta lección es su contrapunto deliberado: muchos de los bucles que sabes escribir no hay que escribirlos. Python trae de fábrica un puñado de funciones que ya los llevan dentro — más rápidas, más cortas y, sobre todo, más fáciles de leer.

El objetivo de esta lección no es memorizar setenta funciones. Es entrenar un reflejo: cuando estés a punto de escribir un bucle, preguntarte «¿existe ya una función que haga esto?». Casi siempre, sí.

1. Qué son, y cómo descubrirlas tú mismo

Las built-in functions son las que están disponibles siempre, sin escribir un solo import. Ya usas varias sin pensarlo: print(), len(), range(), sorted().

No te fíes de ninguna lista que te den (tampoco de esta). Compruébalo tú mismo en tu propio intérprete: 

import builtins

# Todas las funciones siempre disponibles, en orden alfabético
funciones = [n for n in dir(builtins)
             if callable(getattr(builtins, n)) and not n.startswith("_")]
print(len(funciones))
print(sorted(funciones))

# Y para saber qué hace cualquiera de ellas, sin salir de Python:
help(divmod)
Un detalle honesto sobre el número. Verás citado por ahí «Python tiene 71 funciones built-in», pero el número depende de cómo cuentes: algunas (help, exit, quit...) no son del lenguaje, las añade el módulo site al arrancar el intérprete interactivo. Ejecutando el código de arriba con python3 -S (que no carga site) salen 69 en Python 3.14. La documentación oficial es deliberadamente vaga: dice «una serie de funciones», sin dar cifra. Lección de fondo: verifica en tu versión, no en la memoria de nadie.

2. any() y all(): la estrella de esta lección

Si solo te llevas dos funciones de aquí, que sean estas. Responden a las dos preguntas más frecuentes sobre una colección: ¿alguno cumple? y ¿todos cumplen? 

notas = [88, 72, 95]

# El bucle que ya NO escribes:
alguno_aprobado = False
for n in notas:
    if n >= 50:
        alguno_aprobado = True
        break

# La versión con built-in:
alguno_aprobado = any(n >= 50 for n in notas)   # True
todos_aprobados = all(n >= 50 for n in notas)   # True

Fíjate en lo que va dentro del paréntesis: n >= 50 for n in notas es una expresión generadora — produce True/False uno a uno, sin construir ninguna lista intermedia. Es el mismo mecanismo perezoso de la lección 014.

Se paran en cuanto lo saben (short-circuit)

any() deja de mirar en cuanto encuentra el primer True; all(), en cuanto encuentra el primer False. No recorren el resto. Comprobado espiando qué elementos llegan a leer de verdad:

LlamadaElementos que llega a leerResultado
any([False, True, False, False])[False, True] — y paraTrue
all([True, False, True, True])[True, False] — y paraFalse

Esto importa de verdad cuando cada elemento cuesta caro de calcular: una consulta a base de datos, una llamada a una API, o una comprobación sobre un fichero enorme.

El caso vacío, que sorprende a todo el mundo

any([]) devuelve False.
all([]) devuelve True.

El primero es intuitivo: en una lista vacía no hay ninguno que cumpla. El segundo desconcierta, pero es lógicamente correcto y tiene nombre propio en lógica: verdad vacua. La pregunta que responde all() es «¿hay algún elemento que incumpla?». Si no hay elementos, no hay ninguno que incumpla → True.

Dónde te va a morder esto. Si escribes if all(candidato_es_valido(c) for c in candidatos): y la lista candidatos llega vacía por un error previo, tu código dirá alegremente que «todos son válidos» y seguirá adelante. Cuando el caso vacío signifique un problema, compruébalo aparte: if candidatos and all(...).

Conectándolo con tu curso

En el Módulo 3 (lección 004) escribiste es_matching_estable() recorriendo todas las parejas en busca de un par bloqueante. Ese bucle es exactamente un any() disfrazado: 

# "Es estable si NO existe ningún par bloqueante"
def es_matching_estable(prefs_p, prefs_r, matching):
    return not any(es_par_bloqueante(prefs_p, prefs_r, matching, p, r)
                   for p in matching
                   for r in prefs_r
                   if matching[p] != r)

3. min() y max(): key y default

Ya los usas para números. Sus dos parámetros extra son los que casi nadie conoce y los que te ahorran el bucle: 

palabras = ["sol", "ventana", "mar"]
max(palabras, key=len)              # 'ventana' — la más larga

candidatos = {"Ana": 88, "Carlos": 72, "Lucía": 95}
max(candidatos, key=candidatos.get) # 'Lucía' — la clave con mayor valor

# 'default' evita el error con colecciones vacías
min([], default="sin datos")        # 'sin datos'
min([])                             # ValueError: min() iterable argument is empty

key es la misma idea que aprendiste en la lección 002 con sorted(): una función que dice por qué criterio comparar. Y como allí, en caso de empate gana el primero que aparece.

4. sum() y su tercer uso inesperado

sum([1, 2, 3])          # 6
sum([1, 2, 3], 10)      # 16  — el 2º argumento es el valor inicial

# Contar cuántos cumplen una condición, sin bucle ni contador:
notas = [88, 72, 95]
sum(n >= 80 for n in notas)     # 2  — porque True vale 1 y False vale 0

Ese último idioma es muy usado: como bool es una subclase de int en Python, sumar booleanos cuenta cuántos son verdaderos.

sum() también concatena listas (sum([[1,2],[3]], []) → [1, 2, 3]), pero no lo hagas: es O(n²) porque crea una lista nueva en cada paso. Para eso está itertools.chain(), que viste en la lección 016.

5. zip(strict=True): el bug silencioso

zip() empareja elementos de dos colecciones. El problema es qué hace cuando no miden lo mismo: trunca sin avisar. 

nombres = ["Ana", "Carlos", "Lucía"]
notas   = [88, 72]                     # ¡falta una!

list(zip(nombres, notas))
# [('Ana', 88), ('Carlos', 72)]        ← Lucía desaparece EN SILENCIO

list(zip(nombres, notas, strict=True))
# ValueError: zip() argument 2 is shorter than argument 1
Cuando las dos colecciones deberían medir lo mismo (candidatos y sus notas, claves y valores...), usa siempre strict=True. Convierte un bug que se descubre semanas después en un error que salta al instante. Disponible desde Python 3.10 (PEP 618).

6. El resto del kit imprescindible

# enumerate con inicio distinto de 0 — para listados humanos
list(enumerate(["Ana", "Carlos"], start=1))
# [(1, 'Ana'), (2, 'Carlos')]

# divmod: cociente y resto de una vez (devuelve una tupla)
divmod(17, 5)        # (3, 2)   — 17 = 3*5 + 2
minutos, segundos = divmod(125, 60)    # (2, 5) → "2 min 5 s"

# abs y pow
abs(-7)              # 7
pow(2, 10)           # 1024  — igual que 2 ** 10
pow(2, 10, 1000)     # 24    — (2**10) % 1000, en un solo paso eficiente

# reversed: al revés, pero SIN copiar la lista
list(reversed([1, 2, 3]))   # [3, 2, 1]
[1, 2, 3][::-1]             # [3, 2, 1] — mismo resultado, pero crea una copia
reversed() vs [::-1]: el slicing construye una lista nueva completa en memoria; reversed() devuelve un iterador perezoso que no copia nada. Para tres elementos da igual; para tres millones, no. Si solo vas a recorrerla una vez, reversed().

Compruébate antes de seguir

Responde mentalmente antes de desplegar cada respuesta — el esfuerzo de recordar es lo que fija el conocimiento, mucho más que releer.

¿Qué devuelve all([]), y por qué?

Devuelve True. La pregunta que responde all() es si existe algún elemento que incumpla la condición; en una colección vacía no existe ninguno que incumpla, así que la respuesta es afirmativa. Se llama verdad vacua.

¿Cuántos elementos lee any() sobre [False, True, False]?

Dos. Se detiene en cuanto encuentra el primer valor verdadero, sin llegar a evaluar el tercer elemento. Es el comportamiento llamado short-circuit, y ahorra trabajo cuando cada elemento es costoso.

¿Qué pasa con zip(["a","b","c"], [1,2]) sin strict?

Trunca silenciosamente al más corto y devuelve dos pares, perdiendo el tercer elemento sin avisar de nada. Con strict=True, en cambio, lanza un ValueError inmediato indicando que un argumento es más corto.

¿Por qué reversed(x) gasta menos memoria que x[::-1]?

Porque devuelve un iterador perezoso que recorre la secuencia original de atrás hacia delante, sin construir nada. El slicing, en cambio, materializa en memoria una lista nueva completa con todos los elementos copiados.
