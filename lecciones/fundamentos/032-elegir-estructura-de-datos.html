Elegir la estructura de datos correcta

Lista, tupla, diccionario o conjunto — la decisión que cambia tu código de 516 ms a 0,02 ms

Python te da cuatro estructuras básicas y casi siempre puedes resolver el problema con cualquiera de ellas. Por eso es fácil coger siempre la lista y seguir adelante. Esta lección va de lo contrario: de tener criterio para elegir a conciencia, porque la diferencia no es estética — es de varios órdenes de magnitud.

1. Las cuatro, en una tabla

EstructuraSintaxis¿Mutable?¿Ordenada?¿Duplicados?Para qué
list[1, 2, 3]SíSíSíSecuencia que cambia
tuple(1, 2, 3)NoSíSíRegistro fijo, clave de dict
dict{"a": 1}SíSí*Claves noBuscar por clave
set{1, 2, 3}SíNoNoPertenencia, deduplicar

* Los diccionarios conservan el orden de inserción desde Python 3.7 (nota oficial). Los conjuntos no conservan ningún orden.

2. La pregunta que decide casi todo: «¿está ahí dentro?»

Comprobar si un elemento pertenece a una colección es lo más frecuente que vas a hacer. Y es donde lista y conjunto se separan brutalmente. 

# Lista: Python recorre elemento a elemento hasta encontrarlo → O(n)
objetivo in lista

# Conjunto: Python calcula el hash y va directo al sitio → O(1)
objetivo in conjunto

No te fíes de la teoría: esto es medido en Python 3.14, buscando el último elemento (el peor caso para la lista), 1.000 veces:

TamañoEn una listaEn un conjuntoDiferencia
1.0005,3 ms0,025 ms210× más rápido
100.000516,4 ms0,023 ms22.493× más rápido
Fíjate en la columna del conjunto: no cambia al multiplicar por 100 el tamaño. Eso es lo que significa O(1). La lista, en cambio, tarda 100 veces más — eso es O(n). Es exactamente el contraste que viste en Quicksort, pero aquí lo ganas gratis solo con elegir bien el tipo.

Pero nada es gratis: la memoria

100.000 enteros en...Memoria
list800.056 bytes
tuple800.048 bytes
set4.194.520 bytes (≈5×)

El conjunto paga con memoria la velocidad de búsqueda: necesita espacio libre para que la tabla hash funcione bien. Es el compromiso clásico tiempo contra espacio.

Regla práctica: si vas a preguntar «¿está?» muchas veces sobre los mismos datos, convierte una vez a set y consulta mil. Si solo preguntas una o dos veces, no compensa ni el tiempo de construirlo.

3. Tuplas: no son «listas de segunda»

La tupla no es una lista capada. Es una estructura distinta que comunica algo al que lee: esto no va a cambiar. 

punto = (3, 7)              # un registro: x e y juntos tienen sentido
colores = ["rojo", "azul"]  # una colección: podrían ser 2 o 200

x, y = punto                # unpacking: se lee muy bien

Y tienen una capacidad que las listas no pueden tener:

# Solo lo inmutable puede ser clave de un dict o elemento de un set
distancias = {("Sevilla", "Cádiz"): 125}    # ✅ tupla como clave
distancias = {["Sevilla", "Cádiz"]: 125}    # ❌ TypeError: unhashable type
No es un capricho: si la clave pudiera cambiar después de guardarla, el diccionario ya no sabría en qué cajón la metió. Por eso solo lo inmutable es hashable. Lo viste en la lección 011 desde el ángulo funcional; aquí es la consecuencia práctica.

4. Conjuntos: el álgebra que te ahorra bucles anidados

aptos    = {"Ana", "Carlos", "Lucía"}
inscritos = {"Carlos", "Lucía", "Jorge"}

aptos & inscritos    # {'Carlos', 'Lucía'}  — en ambos (intersección)
aptos | inscritos    # los cuatro           — en alguno (unión)
aptos - inscritos    # {'Ana'}              — aptos que NO se inscribieron
aptos ^ inscritos    # {'Ana', 'Jorge'}     — en uno pero no en el otro

Cada una de esas líneas sustituye un bucle anidado con condiciones. Si alguna vez escribes for a in lista1: for b in lista2: if a == b:, párate: eso es una intersección.

El precio del conjunto: pierde el orden

datos = [3, 1, 3, 2, 1, 5]

list(set(datos))            # [1, 2, 3, 5]  ← deduplica pero DESORDENA
list(dict.fromkeys(datos))  # [3, 1, 2, 5]  ← deduplica y CONSERVA el orden
Ese dict.fromkeys() es el idioma estándar para deduplicar conservando el orden de aparición. Funciona porque las claves de un dict son únicas y, desde 3.7, ordenadas.

5. Diccionarios: cuando los datos tienen nombre

Si te encuentras recordando que «la posición 0 es el nombre y la 2 es la nota», necesitas un diccionario: 

candidato = ["Ana", 28, 88]        # ¿qué era el 28? ¿la edad? ¿el orden?
candidato["nota"]                   # esto se lee solo

Y el patrón más frecuente, contar cosas:

from collections import Counter
Counter(["a", "b", "a"]).most_common(1)    # [('a', 2)]

# defaultdict: agrupar sin comprobar si la clave existe
from collections import defaultdict
por_destino = defaultdict(list)
por_destino["Sevilla"].append("Ana")   # no hace falta inicializar la clave

Cómo decidir, en cuatro preguntas

1. ¿Los datos tienen nombre (clave → valor)? → dict

2. ¿Solo me importa si están, y no quiero duplicados? → set

3. ¿Es un registro fijo, o lo necesito como clave? → tuple

4. Para todo lo demás → list

Compruébate antes de seguir

¿Por qué buscar en un set no se ralentiza al crecer?

Porque calcula el hash del elemento y salta directamente a la posición donde debería estar, en lugar de recorrer los elementos uno por uno. El tiempo no depende de cuántos elementos haya guardados: eso es lo que significa la notación O(1).

¿Por qué una lista no puede ser clave de un diccionario?

Porque las listas son mutables y el diccionario localiza cada clave por su hash. Si la clave cambiara después de guardarla, su hash cambiaría y el valor quedaría perdido en un cajón equivocado. Solo lo inmutable es hashable.

¿Qué se pierde al hacer list(set(datos)) para deduplicar?

Se pierde el orden original de aparición de los elementos, porque los conjuntos no conservan ninguna ordenación. Si necesitas conservarlo, el idioma correcto es list(dict.fromkeys(datos)), que aprovecha que las claves son únicas y ordenadas.

Ejercicio práctico

Elige bien, y mídelo

Siete funciones donde la estructura elegida es la equivocada: bucles anidados que son intersecciones, listas usadas como índices de búsqueda, deduplicaciones que destrozan el orden. Reescríbelas eligiendo la estructura correcta — y al final, mide tú mismo la diferencia.
