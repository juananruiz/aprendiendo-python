Errores y excepciones

Fallar bien: capturar lo justo, protestar pronto y no esconder nunca un problema

Hasta ahora tus scripts han vivido en un mundo amable: los datos llegaban bien y los ficheros existían. En cuanto automatices algo de verdad — leer un CSV que alguien editó a mano, llamar a una API que a veces no responde — el manejo de errores deja de ser teoría. Esta lección va de eso.

La tentación al aprender excepciones es envolverlo todo en un try gigante para que «no pete». Eso no arregla nada: solo convierte un error ruidoso en un dato corrupto silencioso. El objetivo es el contrario — capturar solo lo que sabes manejar.

1. El esqueleto completo

try:
    numero = int(entrada)
except ValueError:
    print("Eso no es un número")
else:
    print(f"Perfecto: {numero}")     # solo si NO hubo excepción
finally:
    print("Esto se ejecuta siempre") # haya ido bien o mal

El orden real de ejecución, comprobado paso a paso:

SituaciónBloques que se ejecutan
No hay errortry → else → finally
Hay error capturadotry → except → finally

finally se ejecuta siempre: incluso si dentro del try hay un return, o si la excepción no se captura y el programa va a morir. Por eso es el sitio de cerrar ficheros y soltar recursos.

¿Para qué sirve else? Para dejar en el try solo la línea que puede fallar. Si metes también el código de después, podrías capturar sin querer un ValueError que venga de otro sitio y creer que fue la conversión.

2. Captura lo específico, no lo que pilles

# ❌ Esconde cualquier problema, incluidos tus propios bugs
try:
    procesar(datos)
except:
    pass

# ❌ Casi igual de malo: capturas errores que no sabes manejar
except Exception:
    pass

# ✅ Dices exactamente qué esperas que pueda fallar
except (ValueError, KeyError) as e:
    print(f"Dato inválido: {e}")

Además, el orden importa: Python prueba los except de arriba abajo y se queda con el primero que encaje. Si pones el genérico primero, los específicos de debajo no se ejecutan nunca: 

try:
    config["puerto"]
except Exception:      # ← este captura TODO
    ...
except KeyError:       # ← muerto: nunca se llega aquí
    ...
Regla: del más específico al más general, siempre.

Por qué except: a secas es peor que except Exception:

Comprobado en el intérprete:

issubclass(KeyboardInterrupt, Exception)      # False
issubclass(KeyboardInterrupt, BaseException)  # True

Ctrl+C lanza KeyboardInterrupt, que no hereda de Exception. Por eso except Exception te deja cancelar el programa, mientras que un except: desnudo también se traga tu Ctrl+C y deja el script inmortal.

3. La jerarquía (y cómo aprovecharla)

Las excepciones son clases que heredan unas de otras. Verificado:

KeyError          → LookupError    → Exception → BaseException
IndexError        → LookupError    → Exception → BaseException
FileNotFoundError → OSError        → Exception → BaseException
ZeroDivisionError → ArithmeticError→ Exception → BaseException
ValueError                         → Exception → BaseException

Esto no es trivia: capturar el padre captura a todos sus hijos. Como KeyError e IndexError comparten LookupError, un solo except los cubre a ambos: 

try:
    valor = datos[clave]     # da igual si datos es dict o lista
except LookupError:
    valor = None

4. Lanzar tus propios errores con raise

def dividir(a, b):
    if b == 0:
        raise ValueError("El divisor no puede ser 0")
    return a / b

Fallar pronto y con un mensaje claro es un favor a tu yo futuro. Un ValueError con contexto en la línea 3 es infinitamente mejor que un NaN propagándose hasta el informe final.

Excepciones propias

class SaldoInsuficienteError(Exception):
    """La cuenta no tiene fondos suficientes."""

def retirar(saldo, cantidad):
    if cantidad > saldo:
        raise SaldoInsuficienteError(f"saldo {saldo}, intento {cantidad}")
    return saldo - cantidad

Merece la pena cuando quien llama necesita distinguir tu error de los genéricos del lenguaje para reaccionar distinto.

raise ... from: no borres la pista original

def leer_config(config):
    try:
        return config["puerto"]
    except KeyError as e:
        raise ValueError("falta la clave 'puerto' en la config") from e

El from e conserva la excepción original en __cause__, y el traceback muestra ambas. Sin él, pierdes la causa real del problema justo cuando más falta te hace.

5. EAFP: el estilo de Python

Hay dos filosofías para el código que puede fallar, y Python tiene una preferida:

LBYL — mira antes de saltarEAFP — pide perdón, no permiso
if "puerto" in config:
    p = config["puerto"]
else:
    p = 8080
 
try:
    p = config["puerto"]
except KeyError:
    p = 8080

EAFP (Easier to Ask Forgiveness than Permission) es el estilo idiomático en Python, y no es solo gusto: entre el if y el uso, las cosas pueden cambiar (un fichero que existe al comprobarlo y desaparece al abrirlo). Con try no hay hueco.

Para el caso concreto del diccionario, además, ya conoces el atajo: config.get("puerto", 8080). La built-in gana a las dos versiones — otra vez la lección 031.

Compruébate antes de seguir

¿Cuándo se ejecuta el bloque else de un try?

Únicamente cuando el bloque try terminó sin lanzar ninguna excepción. Sirve para separar el código que puede fallar del que solo debe correr si todo fue bien, evitando capturar por accidente errores que vengan de otras líneas.

¿Por qué except: desnudo es peor que except Exception:?

Porque captura también las que heredan directamente de BaseException, como el KeyboardInterrupt que lanza Ctrl+C. El resultado es un programa que ni siquiera puedes cancelar a mano, además de esconder cualquier fallo real.

¿Qué aporta escribir raise ValueError(...) from e?

Conserva la excepción original como causa en el atributo __cause__, de modo que el traceback muestra ambos errores encadenados. Sin ese from, se pierde la pista de qué falló realmente por debajo.

¿Qué significa que Python prefiera EAFP frente a LBYL?

Que resulta más idiomático intentar la operación y capturar el fallo que comprobar antes todas las condiciones. Evita además la ventana temporal en la que el estado puede cambiar entre la comprobación previa y el uso real del recurso.
