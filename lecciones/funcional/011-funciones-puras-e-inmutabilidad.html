Funciones puras e inmutabilidad

Pista 4, lección 1 — el cambio de aires empieza aquí

En 1936, dos personas resolvieron el mismo problema de dos maneras incompatibles. Alan Turing imaginó una máquina con una cinta: un estado que se lee, se modifica y se vuelve a escribir, paso a paso. Alonzo Church imaginó el cálculo lambda: sólo funciones, aplicadas unas a otras, sin ninguna cinta que modificar.

Ambos modelos calculan exactamente lo mismo. Pero de la máquina de Turing salieron C, Java, PHP y el Python que ya escribes. Del cálculo lambda salieron Lisp, Haskell y el Python que vas a aprender en esta pista.

Por qué estás aquí

En OOP clásico (PHP, Java...) trabajas en modo objeto: creas un $empleado, le cambias el estado con $empleado->setDestino(...), y el objeto recuerda lo que le ha pasado. Ese es el mundo de Turing: hay una cinta, y la vas modificando.

La programación funcional dice algo casi ofensivo: no cambies nada nunca. En lugar de modificar el empleado, produce un empleado nuevo. En lugar de acumular en una variable, devuelve un valor. En lugar de tener estado, ten funciones.

Esta pista no es sobre sintaxis de Python. Es sobre desactivar un reflejo mental que llevas años entrenando, para poder elegir conscientemente cuándo usarlo.

Qué es una función pura

Una función es pura si cumple dos condiciones:

1. Determinismo. Con los mismos argumentos, siempre devuelve el mismo resultado. Siempre. Sin excepciones ni «depende».

2. Sin efectos secundarios. No modifica nada fuera de sí misma: ni variables globales, ni sus propios argumentos, ni ficheros, ni la base de datos, ni la pantalla.

Una función pura, vista desde fuera, es indistinguible de una tabla de consulta. Podrías sustituirla por un diccionario gigante con todas las respuestas precalculadas y el programa se comportaría igual. Eso se llama transparencia referencial, y es la propiedad de la que sale todo lo demás.

Pura

def puntuacion_total(experiencia, formacion, idiomas):
    """Baremo de una oposición. Mismos méritos → misma nota. Siempre."""
    return experiencia * 0.5 + formacion * 0.3 + idiomas * 0.2

Llámala mil veces con los mismos números y obtendrás mil veces lo mismo. No importa el orden en que la llames, ni cuántas veces, ni desde qué hilo.

Impura — tres formas de romperlo

total = 0

def acumular(nota):
    global total
    total += nota        # ❌ efecto secundario: toca una variable de fuera
    return total         # ❌ y por eso ya no es determinista

from datetime import date

def antiguedad(fecha_ingreso):
    return date.today().year - fecha_ingreso.year   # ❌ no determinista

Esta última es especialmente traicionera: no modifica nada, pero lee del mundo exterior. Hoy devuelve 12, el 1 de enero devolverá 13. No puedes escribir un test estable sobre ella.

La versión pura es recibir el dato en vez de ir a buscarlo: def antiguedad(fecha_ingreso, hoy): return hoy.year - fecha_ingreso.year. El impuro pasa a ser quien la llama — y eso es exactamente lo que queremos: empujar la impureza hacia los bordes del programa. 
def ordenar_candidatos(candidatos):
    candidatos.sort(key=lambda c: c["nota"])   # ❌ muta el argumento
    return candidatos

Esta tercera es la que más disgustos da en Python. Quien llama a ordenar_candidatos(mi_lista) espera recibir una lista ordenada — y no espera que mi_lista haya cambiado a su espalda. La versión pura usa sorted(), que devuelve una lista nueva: 

def ordenar_candidatos(candidatos):
    return sorted(candidatos, key=lambda c: c["nota"])   # ✅ lista nueva
Regla mnemotécnica de la librería estándar: los métodos que mutan devuelven None (lista.sort(), lista.append(), lista.reverse()). Las funciones puras devuelven el resultado (sorted(), reversed(), lista + [x]). Si escribes x = lista.sort() y te sale None, acabas de tropezar con esta regla.

Qué te compra la pureza

PropiedadPor qué te importa
Testeable Sin mocks, sin base de datos, sin fixtures. Entrada → salida. Es la Pista 3 de testing hecha trivial.
Razonable en local Para entender la función te basta con leer la función. No tienes que reconstruir mentalmente el estado del programa.
Cacheable Si el resultado sólo depende de los argumentos, se puede memorizar. Eso es literalmente @lru_cache (lección 015), y sólo es correcto sobre funciones puras.
Paralelizable Sin estado compartido no hay condiciones de carrera. Se acabaron los locks.
Componible Puedes encadenarlas sin miedo, porque ninguna sabota a la siguiente. Es el tema de la lección 012.

Inmutabilidad

La pureza es una propiedad de las funciones. La inmutabilidad es la propiedad de los datos que la hace fácil de conseguir: si tus datos no se pueden cambiar, ninguna función puede mutarlos por accidente.

Python ya te da los dos grupos:

InmutablesMutables
int, float, str, bool, tuple, frozenset, bytes list, dict, set, bytearray, la mayoría de tus clases 
nombre = "ana"
nombre.upper()        # devuelve "ANA" — NO modifica nombre
print(nombre)         # "ana"  ← los strings son inmutables

notas = [7, 9, 5]
notas.append(8)       # SÍ modifica notas
print(notas)          # [7, 9, 5, 8]  ← las listas son mutables

Crear en vez de mutar

# Estilo imperativo: modificar en el sitio
candidato["destino"] = "Sevilla"

# Estilo funcional: construir uno nuevo
candidato_asignado = {**candidato, "destino": "Sevilla"}

El operador ** desempaqueta el diccionario original y las claves que escribes después ganan. El original queda intacto. Para listas:

asignados_ahora = [*asignados, nuevo]     # en vez de asignados.append(nuevo)
sin_el_primero  = pendientes[1:]          # en vez de pendientes.pop(0)
ordenados       = sorted(candidatos, key=...)   # en vez de candidatos.sort()
«Pero eso copia toda la lista, será lentísimo». A veces sí, y por eso el deque de la lección 003 existe. Pero antes de optimizar, mide: para las decenas o cientos de elementos con los que trabajas en una asignación de plazas, el coste es irrelevante y la claridad que ganas no lo es. La optimización prematura sigue siendo la raíz de todo mal.

Tuplas y frozenset

plaza = ("Sevilla", "A2", 3)      # tupla: no se puede tocar
plaza[0] = "Cádiz"                # TypeError

# Bonus: sólo lo inmutable puede ser clave de un dict o elemento de un set
preferencias = {("Sevilla", "A2"): 1, ("Cádiz", "A2"): 2}   # ✅
preferencias = {["Sevilla", "A2"]: 1}                        # TypeError ❌
Un objeto es hashable (usable como clave) sólo si es inmutable. No es una restricción arbitraria: si la clave pudiera cambiar, el diccionario ya no sabría en qué cajón la guardó.

Clases inmutables: frozen=True

Cuando necesites un objeto con campos con nombre pero sin estado mutable:

from dataclasses import dataclass, replace

@dataclass(frozen=True)
class Candidato:
    nombre: str
    nota: float

c = Candidato("Ana", 8.5)
c.nota = 9.0                      # FrozenInstanceError ❌
c2 = replace(c, nota=9.0)         # ✅ devuelve un Candidato NUEVO

Compáralo con lo que harías en un lenguaje OOP como PHP: una clase con private $nota y un setNota(). Aquí no hay setter porque no hay nada que setear: hay una fábrica de versiones nuevas.

El gotcha: argumentos por defecto mutables

Este es el error clásico de Python, y es exactamente un fallo de inmutabilidad. Léelo despacio: 

def registrar(nombre, historial=[]):     # ❌ TRAMPA
    historial.append(nombre)
    return historial

print(registrar("Ana"))     # ['Ana']
print(registrar("Carlos"))  # ['Ana', 'Carlos']  😱 ¿de dónde sale Ana?

El valor por defecto se evalúa una sola vez, cuando Python define la función — no cada vez que la llamas. Esa lista es un único objeto compartido por todas las llamadas, y al mutarla lo arrastras entre llamadas. 

def registrar(nombre, historial=None):   # ✅ el idioma correcto
    historial = historial or []
    return [*historial, nombre]          # y además, sin mutar nada
Si nunca mutas los argumentos, este bug no puede existir. El estilo funcional no es sólo elegante: elimina categorías enteras de error por construcción.

Cuándo NO ser purista

Un programa 100 % puro no sirve para nada: no imprime, no guarda, no lee. Los efectos secundarios son el objetivo del programa. Lo que buscamos no es eliminarlos, sino concentrarlos:

Núcleo funcional, cáscara imperativa. El corazón que calcula es puro y se testea trivialmente. La cáscara fina que lee ficheros, llama a APIs e imprime es impura y se testea con integración.

def main():                                    # cáscara: impura
    datos = leer_csv("candidatos.csv")         # ← efecto: I/O
    resultado = asignar_plazas(datos)          # ← núcleo: 100 % puro
    escribir_csv("asignacion.csv", resultado)  # ← efecto: I/O

Fíjate en la asimetría: asignar_plazas puede tener 300 líneas de lógica delicada y se testea sin tocar el disco. Las dos líneas impuras son triviales. Eso es todo el truco.
